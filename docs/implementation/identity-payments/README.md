# 邮箱、微信与商户支付交付

此分支基于新版 C4 后台，完整源码包包含前台、后台、API、小程序、接口合同、SQL 与服务器测试栈。由本地 Codex 在 `/www/wwwroot/HuaNian_SheJi` 搭建；云端开发环境未连接用户服务器，也未接入真实邮箱或商户凭据。

## 最终行为

- Web 邮箱验证码登录/首次注册；安全会话 Cookie，邮箱地址加密保存，验证码一次性、五分钟、五次尝试，邮箱与来源发送限流。
- 小程序官方微信身份交换；已有 Web 用户可同时验证邮箱与微信后主动绑定，已有微信用户可为当前账号添加邮箱。另一账号已有身份返回冲突。解绑后，可凭双方新验证重新绑定自己的微信。验证码错误不会误刷新会话、破坏原挑战。
- Web 微信 Native 与支付宝当面付扫码，包含官方签名请求、原始通知/响应验签、查单、关单、原路退款。微信回调先验签再解密。支付宝退款由官方签名原退款查询确认。
- 两渠道沿用不可变订单快照、原有幂等、权益与审计。只有当前发布版本已登记并通过准入的渠道出现在购买入口；历史适配器仍可查单/退款。微信平台公钥支持同商户新旧 serial 重叠验签，独立于订单绑定轮换。
- 提供服务器私有配置、可选单机加密密钥仓、受信任依赖声明和签名查单发布探测。没有默认管理员、默认成功支付或关闭验签的开关。

## 验证

- 全量：72 个测试文件，526 项，通过且无跳过；使用真实本地 PostgreSQL、Redis 与 Chromium。
- 页面：18 项，通过，覆盖邮箱登录/重填邮箱、支付宝入口、原有支付/退款/导出和新版后台交互。
- 类型检查、接口生成一致性、Web/admin 生产构建通过。
- 三个实际 Docker 镜像构建成功，四个服务健康；编辑器/后台/商业页面 HTTP200，Chromium 实际加载编辑器与后台无 JavaScript 错误。
- SQL 与对象文件在容器 stop/up 后保留。旧 C4 数据库（001+C3+002+003+004）含已有用户/微信身份，执行 005 后保留原数据并新增邮箱表。
- 独立审查发现的四项问题均补回归并修复：mini 幂等请求头、同账号微信重绑、历史微信绑定平台验签密钥轮换、购买能力与当前绑定匹配。额外错误验证码→正确验证码的实际 HTTP 回归证明 mini 会话得以保留。

验证曾因开发机根分区写满出现 PostgreSQL ENOSPC；只清理任务生成的临时副本与可重建 Docker 构建缓存后重跑。源码、上传包、密钥及数据库卷保留。最终通过结果取自恢复后的完整运行。

## 实施决定与边界

1. 普通商户扫码与小程序虚拟商品准入分开；普通微信商户号不能代替小程序虚拟支付权限，未单独开通时该入口继续关闭。
2. 文件密钥仓面向单服务器，目录与主密钥须备份；多节点部署须换共享密钥管理服务。
3. 支付宝退款以原退款查单确认，可能等待现有恢复调度周期，不把普通交易通知当作退款成功。
4. 没有真实凭据与用户服务器访问，未宣称邮件送达、商户权限、资金到账或用户服务器迁移已验证。这些需要部署后的真实联调。

没有延期的小问题。部署字段、可信配置发布、密钥轮换及升级步骤见 [服务器接入说明](../../../deploy/server-test/IDENTITY-PAYMENTS.md)。升级旧库只执行 005，不重放初始 SQL，不删除卷。
